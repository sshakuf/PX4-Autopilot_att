Understanding Angular Motion: How Radians Become Physical Movement

"What does angular actually mean? If the drone moves 1 meter in X, what does the sensor see?"

The Core Geometry

Imagine your camera pointing straight down from height h = 2 metres. The drone then moves 1 metre to the right:

    BEFORE          AFTER
      📷     →→→    📷
      |              |
    2m|             2m|
      |              |
   ───A──────────────B───
      ↑              ↑
  target (A)      (now under B)

  The camera is now above B but the target is still at A.
  The sensor sees the target has "shifted" by angle θ.

The camera does not measure "I moved 1 metre". It measures the angle the target has shifted in its field of view:

         📷  (above B)
        /|
       / |
      /  | h = 2m
     /   |
    / θ  |
   A─────B
   |←1m→|

tan(θ) = 1m / 2m  =  0.5
      θ = arctan(0.5)  ≈  0.46 radians  ≈  26.5°
Moving 1 metre at 2m height = 0.46 radians of apparent angular shift.
The same 1 metre at 5m height = only 0.20 radians.
Higher altitude → smaller angular reading for the same physical movement.

The Formula

Angular shift from physical movement θ (radians) = displacement (metres) / height (metres) Recovering physical movement from angle displacement (m) = θ (rad) × height (m)
HeightDrone moves 1 mAngular shift seen by sensor
0.5 m1 m2.00 rad — huge signal
1 m1 m1.00 rad
2 m1 m0.50 rad
5 m1 m0.20 rad
10 m1 m0.10 rad — small signal

What the Sensor Actually Measures

The sensor does not measure a single snapshot angle. Between two frames it counts how many pixels the scene shifted, converts to radians, and accumulates that over a fixed time window:

# Example: target moved 50 pixels in one frame interval
# Camera: 640 px wide, 1.2 rad horizontal FOV

rad_per_pixel = 1.2 / 640  =  0.001875 rad/px

angular_shift = 50 px × 0.001875  =  0.09375 rad  ← this is integrated_x in the MAVLink message

# If this happened in dt = 0.014 s  (70 Hz publishing rate):
angular_rate  = 0.09375 / 0.014   =  6.7 rad/s    ← flow_rate used internally by EKF2

Full Chain: Pixels → Radians → Velocity → Position Hold

Camera sees target shifted 50 pixels
Convert pixels → radians (your code)
  • integrated_x = 50 px × (FOV / resolution) = 0.094 rad
  • Send in OPTICAL_FLOW_RAD MAVLink message
EKF2 divides by dt → angular rate
  • flow_rate = 0.094 rad / 0.014 s = 6.7 rad/s
EKF2 subtracts gyro rotation
  • flow_compensated = flow_rate − gyro_rate
  • Removes rotation-induced apparent flow, leaves only translation
EKF2 multiplies by height → velocity
  • velocity = flow_compensated × height
  • = 6.7 rad/s × 2 m = 13.4 m/s — "drone is moving at 13.4 m/s"
Position controller brakes → target returns to centre → hover
  • Flow goes to 0 when drone is stationary over target
  • Position hold maintained

Why Radians and Not Just Pixels?

Because pixels are meaningless without knowing the camera FOV. A 100-pixel shift on a narrow telephoto lens is a tiny angle. The same 100-pixel shift on a wide-angle lens is a huge angle. Converting to radians makes the measurement camera-independent — PX4 does not need to know your camera specs. You handle that conversion before sending the message.

velocity (m/s) = (integrated_rad / dt_seconds) × height_metres

Overview: What is Optical Flow

Optical flow sensors measure angular motion of the scene below the drone by tracking pixel movement frame-to-frame. The fundamental output is integrated angle change in radians — how much the scene appeared to rotate around each body axis during a time window.

Core Equation:
velocity (m/s) = flow_rate (rad/s) × height_above_ground (m)

This is how PX4 derives position from optical flow — without GPS. If you know how fast the scene appears to rotate, and how high you are, you know how fast you are moving.

A physical optical flow sensor (e.g., PMW3901) tracks pixel shifts between frames, divides by a calibration constant (385 counts/radian for PMW3901) to get angular displacement in radians, then accumulates these over a fixed time window. That accumulated value — not a rate — is what gets sent in the MAVLink message.

  • Gyro compensation: flow_comp = flow_rate − (gyro_rate − gyro_bias)
  • Range: range = hagl / cos(tilt)
  • Body velocity: vel_x = −flow_comp_y × range, vel_y = flow_comp_x × range
  • Sequential X/Y Kalman fusion with innovation gates
  • Publishes uORB: vehicle_optical_flow_vel

  • Uses estimated NED position (pN, pE) and velocity (vN, vE)
  • Optical flow continuously corrects horizontal velocity estimate
  • Position hold maintained above target

Critical: How Flow Becomes Velocity

The complete math chain, verified against the PX4 source:

Step 1 — Gyro Compensation flow_compensated = flow_rate − (gyro_rate − gyro_bias) // Removes rotation-induced apparent flow, leaves only translational Step 2 — Range Estimation range = hagl / R_to_earth(2,2) // hagl / cos(tilt) // Converts angular rate to linear velocity via height above ground level Step 3 — Body Frame Velocity vel_body_x = −flow_compensated_y × range vel_body_y = flow_compensated_x × range // Note: axis swap AND sign inversion from EKF body frame convention Step 4 — EKF Innovation (Fusion) predicted_flow = vel_body / range // Forward model innovation = predicted − measured state_update = Kalman_gain × innovation
Key insight — Gyro source: If you send NaN for all gyro fields in the MAVLink message, PX4 automatically uses its own IMU gyroscope for compensation (EKF2_OF_GYR_SRC = 0 Auto). This is the recommended approach for a CV-based system.

Fusion Starting Conditions

When optical flow fails to start, PX4 logs:

FLOW: Starting conditions FAIL - ctrl:X tilt:X within_dist:X qual:X mag:X tilt_ok:X counter:X terrain_valid:X horiz_aid:X timeout:X
FLOW: Distance check - hagl:X.XX min:X.XX max:X.XX

All of these conditions must pass simultaneously:

ConditionWhat Triggers ItNotes
EKF2_OF_CTRL == 1Parameter setMust set manually
tilt_alignIMU alignedTrue after ~2s flying
hagl ≥ SENS_FLOW_MINHGTNot too closeDefault: 0.08 m
hagl ≤ SENS_FLOW_MAXHGTNot too farDefault: 100 m
quality ≥ EKF2_OF_QMINQuality OKIn-air threshold
flow_rate not saturatedNot too fast< SENS_FLOW_MAXR

terrain_valid OR horiz_aidHeight referenceHard one without GPS

Critical for no-GPS: The condition terrain_valid OR horizontal_aiding_active is the tricky one. Without GPS and without a rangefinder, EKF2 cannot estimate terrain height, so optical flow won't start. Solutions:

1. Use a rangefinder (best) — directly provides HAGL and satisfies this condition
2. Send height in the distance field of OPTICAL_FLOW_RAD — PX4 uses it as terrain estimate
3. Barometer as height reference — works but assumes flat terrain

Position Hold Architecture (No GPS)

When optical flow is the only horizontal aiding source, the EKF enters a constrained mode:

EKF State (no GPS):
  Horizontal velocity (vN, vE)  ← constrained by optical flow measurements
  Horizontal position (pN, pE)  ← integrated from velocity (drifts slowly)
  Altitude                      ← barometer or rangefinder
  Gyro bias, accel bias         ← estimated from redundancy

Dead Reckoning Check:
  if (inertial_dead_reckoning OR isOnlyActiveSourceOfHorizontalAiding(opt_flow)):
      is_flow_required = true
      → EKF MUST fuse flow or reset velocity to flow-derived estimate
      → Prevents unbounded horizontal velocity drift

Position Hold (POSCTL / LOITER mode):
  → Position controller uses estimated pN, pE, vN, vE
  → Optical flow continuously corrects velocity estimate
  → Without GPS: position error grows at IMU drift rate
    but velocity error stays bounded by flow measurements

Building Your Custom Optical Flow Source

Pixel to Radian Conversion

# Camera parameters:
# FOV horizontal: fov_x radians (e.g. 1.2 rad = ~69 degrees for typical camera)
# Resolution:     img_width x img_height pixels

rad_per_pixel_x = fov_x / img_width    # e.g. 1.2 / 640 = 0.001875 rad/px
rad_per_pixel_y = fov_y / img_height

# Target moved by (dx_pixels, dy_pixels) since last message:
integrated_x = dx_pixels * rad_per_pixel_x   # radians accumulated
integrated_y = dy_pixels * rad_per_pixel_y

Complete MAVLink Message Construction

import math
import time

# Track time delta between messages
now_us = int(time.time() * 1e6)
dt_us  = now_us - last_publish_us   # microseconds since last message

# Build OPTICAL_FLOW_RAD
msg = mavlink.MAVLink_optical_flow_rad_message(
    time_usec             = now_us,
    sensor_id             = 0,
    integration_time_us   = dt_us,          # accumulation window
    integrated_x          = integrated_x,   # radians (X axis)
    integrated_y          = integrated_y,   # radians (Y axis)
    integrated_xgyro      = float('nan'),   # Let PX4 use its own IMU gyro
    integrated_ygyro      = float('nan'),
    integrated_zgyro      = float('nan'),
    temperature           = 0,
    quality               = quality,        # 0–255 from your CV confidence
    time_delta_distance_us = dt_us,
    distance              = height_m,       # from rangefinder, or -1.0 if unknown
)
mav.send(msg)

Target Locking Logic

# Your CV algorithm tracks a target (e.g. landing pad) in the camera image.
#
# The KEY INSIGHT: You report the apparent motion of the scene, NOT a command.
# PX4 interprets the flow as "drone is moving at this velocity"
# and the position controller corrects it back to zero.
#
# Target at image center → scene not moving → flow = 0 → drone holds still
# Target drifted 20px    → scene moved 20px → publish that flow → EKF corrects

target_x, target_y = detect_target(frame)      # your CV
cx = frame_width  / 2
cy = frame_height / 2

dx_pixels = target_x - cx   # positive = target right of center = drone drifted left
dy_pixels = target_y - cy   # positive = target below center  = drone drifted back

integrated_x = dx_pixels * rad_per_pixel_x
integrated_y = dy_pixels * rad_per_pixel_y

# Confidence-based quality
quality = int(tracking_confidence * 255)   # 0–255
quality = max(0, min(255, quality))

Height — The Critical Missing Piece

Optical flow alone cannot determine velocity.
The formula is: velocity = angular_rate × height_above_ground
Without height, EKF cannot compute velocity from flow — and flow fusion will not start.
Height SourceAccuracyRecommendation
Dedicated rangefinder (TF-Luna, VL53L1X, Garmin LidarLite...)Best ±1–5cmStrongly recommended
Barometer (EKF2_HGT_REF=0)±1–5mOnly for fixed-height operation
distance field in OPTICAL_FLOW_RADSame as sourceSend height from any source here — PX4 uses it directly for terrain estimation

The easiest path: measure height from your host computer (rangefinder, depth camera, or even barometer) and fill the distance field in every OPTICAL_FLOW_RAD message. No separate MAVLink sensor message needed.

Key Takeaways

01

Send OPTICAL_FLOW_RAD — MAVLink message ID 106. No custom driver needed. PX4's MAVLink receiver handles it natively.

02

integrated_x/y in radians, not pixels. Convert: rad = pixels × (FOV / resolution)

03

Send gyro fields as NaN. PX4 uses its own IMU gyro for rotation compensation automatically.

04

quality field (0–255) directly scales EKF noise. Send 200–255 when CV is confident, lower when target is lost.

05

Height is mandatory. Send it in the distance field. Without height, EKF cannot compute velocity from flow.

06

Publish consistently at 50–100 Hz. Irregular timing disrupts EKF timeline alignment. 70 Hz is ideal.

07

Verify sign convention by moving the drone slowly in a known direction and observing flow sign. Fix with SENS_FLOW_ROT or negate in code.

08

Set EKF2_OF_DELAY to your image processing latency (30–100ms typical for CV). Wrong delay = position oscillation.
